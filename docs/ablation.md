# 路由优化：能借鉴的开源机制与消融实验

目标：在**同一个 router**上，把"效果 / 准确度 / 速度"三件事分别量化，找出哪些改动真的有用。所有数字都能用 `npm run sim:ablate` 复现；模型为 `deepseek-flash`，归属统一 `routed`。

## 1. 调研：五个可迁移的机制

| 项目 | 核心机制 | 迁移到本 router 的做法 | 落地位置 |
|---|---|---|---|
| [Semantic Router](https://github.com/aurelio-labs/semantic-router) | 把请求和"路由话术"编码到向量空间比较；**置信度可校准**，低于阈值就返回 `None`；`Chain` 先问快路由，拿不准再落到慢路由；`Merge` 融合多个路由器 | 级联：寒暄 / 叫停 / 唯一强匹配先用规则判定，其余交给模型（v3、v8）。阈值语义直接照搬："只在更可能对的时候才动作" | `src/sim/variants.ts` 的 `cascade` |
| [RouteLLM](https://github.com/lm-sys/RouteLLM) | 在强/弱模型之间按**成本阈值**路由；级联（先弱后强）与"预测获胜率"统一；阈值要用真实流量校准 | 同上；并把"调用数 / token / 耗时"作为和准确率并列的一等指标 | `src/sim/ablate.ts` |
| [MemGPT / Letta](https://github.com/cpacker/MemGPT) | 上下文当 RAM、外部存储当磁盘：**常驻核心块 + 可检索回想 + 归档**，按需换入 | 票卡从"8 张全量卡"改成"12 条任务指纹（title + keywords + state）"，把上下文留给对话（v4、v7） | `src/lab/assessor.ts` 的 `CardStyle: 'index'` |
| [Mem0](https://docs.mem0.ai/) | 记忆抽取 + 多信号检索（语义 + 关键词 + 实体），ADD-only、检索时排序 | 从标题抽 2–6 个关键词作为任务指纹；级联与索引都用它做匹配 | `src/lab/assessor.ts` 的 `keywordsOf` |
| [GPTCache](https://aclanthology.org/2023.nlposs-1.24.pdf) | 语义缓存：命中即返回，省一次生成 | 决策按请求体哈希落盘缓存；消融实验里可 `--fresh` 绕过，保证计时真实 | `src/sim/llm.ts` |

没有直接采纳的：
- **SetFit / BERT 分类器**：需要训练数据与 GPU；本仓库只有 30 条标注，先用规则级联验证结构，等标注到几百条再上小分类器。
- **OpenAI Agents SDK 的 handoff/guardrail**：它的"把转交建模成工具 + 输入/输出护栏"与现有 `orchestrator_route` 的字段校验同构，没有额外收益。

## 2. 消融设计

七个变体，每次只改一处，全部跑在真实语料（Aime 两个标注窗口，A+B = 30 条用户消息）与合成场景上：

| 变体 | 改动 |
|---|---|
| v0 | 基线：coding 提示词、8 张全量票卡、无 answer、无级联、8 条历史 |
| v1 | + `answer`：允许直接回答，不再 `ignore` 到无声 |
| v2 | 去 coding 化：任务 = "有交付物、需要跟进的事"，`worktree_name` 可选，+ `answer` |
| v3 | 级联：寒暄 / 叫停 / 唯一强匹配先判，其余问模型 |
| v4 | 任务指纹卡：8 张全量票卡 → 12 条 `title + keywords + state` |
| v6 | 无历史：卡片不带对话（8 → 0） |
| v7 | v2 + 级联 + 任务指纹卡 |
| v8 | v2 + 级联（保留全量票卡） |

## 3. 结果

真实窗口（A+B，60 条消息·次，**两次独立采样**）：

| 变体 | 严格正确 | 安全送达 | 串台 | 内联回答 | 模型调用 | prompt token | 耗时 |
|---|---|---|---|---|---|---|---|
| v0 基线 | 45/60 (75%) | 47 (78%) | 0 | 0 | 60 | 59.6k | 110s |
| **v2 去 coding + answer** | **48/60 (80%)** | **52 (87%)** | 0 | **14** | 60 | 67.4k | 134s |
| v8 v2 + 级联 | 46/60 (77%) | 49 (82%) | 1 | 16 | **57** | 63.3k | 128s |
| v7 全组合 | 45/60 (75%) | 49 (82%) | 0 | 17 | **55** | 59.5k | **102s** |

单次采样（同一窗口，用于看单因素方向）：

| 变体 | 严格 | 安全 | 调用 | prompt token | 耗时 |
|---|---|---|---|---|---|
| v0 | 24/30 | 26 | 30 | 30.6k | 72s |
| v1 + answer | 22/30 | 22 | 30 | 30.6k | 72s |
| v3 级联 | 22/30 | 23 | **27** | 26.5k | **60s** |
| v6 无历史 | **15/30** | 22 | 32 | 28.3k | 69s |

合成 `many-tasks`（10 个任务后回头找最早的那个，v4 专测召回）：

| 变体 | 严格 | tickets | 调用 | prompt token |
|---|---|---|---|---|
| v0（8 张全量卡） | 11/12 | **11** | 12 | 14.0k |
| v4（12 条指纹） | 11/12 | **9** | 12 | 13.3k |

`many-tasks` 的 oracle 上界是 12/12；窗口 A/B 的上界分别是 16/16、14/14。

## 4. 结论：哪个改动真的有用

**有用，按影响排序：**

1. **对话历史（v6 反证）**：去掉 8 条历史，严格正确从 24/30 掉到 15/30（−30%），安全送达从 26 掉到 22。上下文是最大的准确率杠杆，比任何提示词技巧都大。**不要把票卡当成唯一上下文。**
2. **`answer` 出口（v1/v2）**：真实流量里约 1/3 是内联问答，v0 用 `ignore` 把它们无声丢掉。加上 `answer` 后 v2 有 14 条被直接回答，安全送达 +5（47→52），严格正确 +3。注意：**只在 coding 提示词上加 `answer` 会反噬**（v1 严格 22/30 < v0 24/30），因为模型会把"该建票的活"也答掉；必须和去 coding 化一起改。
3. **去 coding 化（v2）**：`worktree_name` 与 coding 语境让模型把"跑授权、做对比、审片"判成"没有代码改动，无需建票"。改掉任务定义后，窗口 A 的 GitHub 授权从 4 条 ignore 变成正常建票与续接，v2 是唯一在两个真实窗口都超过基线的变体。
4. **级联（v3/v8）**：调用 −10%、耗时 −12~17%，准确率在噪声范围内不变。真实语料里大部分消息没有关键词重合，规则只能拦下寒暄/叫停/唯一命中，所以收益有限；换成 embedding 首判（Semantic Router 的做法）应该能拦下更多。
5. **任务指纹卡（v4）**：在 `many-tasks` 上把重复建票从 11 张压到 9 张，token 少 5%；但在密集的真实窗口上不如全量卡（v7 与 v8 的差距），因为 160 字报告预览和状态细节被压掉了。**建议：票数 ≤ 8 用全量卡，超过 8 用指纹卡 + 按需召回（MemGPT 的分层思路），而不是二选一。**

**没有收益或暂不采纳：**

- v1 单独加 `answer`：反噬（见上）。
- v7 全组合：调用最省（55）、耗时最低（102s），但准确率回落到基线；指标之间是**此消彼长**，不能只看一个数。
- 级联的"关键词唯一命中"在真实中文口语上很脆（指代上一版视频的说法与标题"审片"没有共同词）；这条路要走通需要 embedding。

## 5. 推荐配置

```
ownership: routed                     # 13% → 80%（真实窗口，v2）
prompt: neutral（去 coding 化）        # +3 严格 / +5 安全
allowAnswer: true                     # 14/60 不再被无声丢掉
history: 8（不要降到 0）               # 去掉会掉 30% 严格正确
card: 全量 8 张；超过 8 张时切指纹卡    # many-tasks 重复 11 → 9
cascade: 规则首判（寒暄/叫停/唯一命中）  # 调用 −10%，准确率不变
```

对应的一份实现就是 v8 + 动态卡片；如果更看重准确率而不是调用成本，用 v2。


## 8. 三个缺口的修复与验证（第六轮）

上一版结论里留了三个缺口，这一轮都做成了可开关的实现，并在同一套语料上验证。

| 缺口 | 修复 | 验证 |
|---|---|---|
| 被拒的路由命令锁住整个 Thread | `Engine.attach` 在拒绝后**用第二个事务** `releaseRouting`（第一个事务已回滚）；`orchestrator_route` 对任何 `UserError` 调用 `host.release`；被拒的 Trigger 记一条 `ignore{notAttachable}` | 两个测试：拒绝后 `evaluating` 为空、下一条消息立刻拿到卡片；`Engine.attach` 直连调用也会自愈 |
| 一条 accept 决定整批 | 两个开关：`acceptBatch: 'primary'`（只接收当前 Trigger，其余重新排队）与 `batchSplitter`（按相邻消息相似度切批，`splitBatches`） | 三条无关请求同批：默认 **1/3、swept 2**；`primary` **3/3、swept 0**；`splitter` **3/3、swept 0**。真实模型同一份"三个 accept"的输出，在 `primary` 下真的产出 3 张票 |
| 第 9 个任务起不可见 | 卡片 = 最近 8 张 + 关键词命中的旧票（最多 4 张，标 `recall: 'keyword'`） | `many-tasks` 严格 10.3 → **11.3/12**（三次采样），重复建票消失；无关键词重合时卡片仍是 8 张 |
| 级联首判从关键词换成 embedding | 无依赖的哈希 n-gram embedding（512 维，2–3 gram，L2 归一化）+ 上下文（最近两条消息）+ 阈值 0.14 / 间隔 0.02（在窗口 A 校准，窗口 B 验证 0 误判） | **负结果**：v3e 36/60、6 条串台；v8e 19/60、27 条串台，比关键词级联更差。原因有二：这个"embedding"只是平滑的词面重合，不是语义向量；阈值是在 fixture 的短标题上校准的，换到模型生成的长标题后分布漂移。实现保留、默认关闭 |

结论：**前三个缺口可以关掉，第四个不能。** 级联的结构是对的，但首判必须换成真正的向量模型，并且必须在**线上票标题**上重新校准阈值；哈希 n-gram 只能证明结构，不能带来收益。

新增开关（默认全关，行为与原实现一致）：

```ts
new Engine({ ..., acceptBatch: 'primary', batchSplitter: splitBatches })
new Lab({ ..., cardStyle: 'index', acceptBatch: 'primary', batchSplitter: splitBatches })
```

测试从 34 增至 **37**：拒绝释放、`primary` 单批多票、切批、召回、embedding 排序、向量级联拦截。

## 6. 复现

```bash
cd ~/workspace/router
npm run sim:ablate                       # 全矩阵（默认缓存）
node --experimental-transform-types --no-warnings src/sim/ablate.ts --fresh \
  --variants v0,v2,v7,v8 --scenarios aime-a,aime-b --repeat 2   # 真实窗口，两次独立采样
```

数字来自 2026-11-14 的一次运行；`deepseek-flash` 在 30 条真实消息上的采样波动约 ±2 条，因此报告里同时给了单次与两次采样的结果。原始输出可用 `--out` 重新生成。

## 7. 这套消融的边界

- 每个变体只测 30 条真实消息（两个窗口），合成场景 16/12 条；小样本下单条差异就是 3%，结论要看方向而不是小数点。
- 级联用的是关键词而不是 embedding（本仓库没有 embedding 依赖），所以它是**级联结构的下界**。
- `answer` 在本仓库里是宿主行为（直接写 Outbox），因为核心的 `Replies.answer` 要求"某个 worker 的回答"，没有票的内联回答无法走通 —— 这正是建议补成一等结果的原因。
- 成本只算 token 与墙钟时间，没有算网关/重试；`deepseek-v4-pro` 未参与消融（单次约 8.5s，跑完整矩阵成本过高）。
